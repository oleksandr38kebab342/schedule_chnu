# Концепція продукту

**Проєкт:** Інформаційна система управління та відображення навчального розкладу
**Спринт 0** · відповідальні: БА + PM + UI/UX + техліди + ментор · джерело: ТЗ v1.0

## 1. Ідея одним реченням
Централізований вебзастосунок, у якому диспетчери формують і перевіряють розклад університету, а студенти й викладачі щодня бачать його актуальним (зокрема на телефоні) і можуть вивантажити його в Excel для друку.

## 2. Проблема
Розклад живе в розрізнених Excel/Word-файлах: конфлікти (група, викладач, аудиторія) знаходять постфактум, заміни й перенесення губляться між версіями, нестандартні аудиторії (`А.203А` / `А203А` / `А-203А`) і час пар не зводяться до єдиного вигляду, немає журналу «хто і що змінив».

## 3. Цільові користувачі
| Група | Що їм потрібно |
|---|---|
| Диспетчери та адміністратори (факультет, кафедра) | Швидко складати й правити розклад, бачити конфлікти, вивантажувати Excel |
| Викладачі | Особистий розклад, аудиторії, зміни |
| Студенти | Розклад групи / підгрупи / потоку, екран «Сьогодні» на телефоні |

## 4. Ключова цінність
1. **Розклад — не таблиця, а модель:** заняття = дисципліна + тип + групи/підгрупи/потоки + викладачі + аудиторії + день + пара + семестр + модель тижнів + винятки.
2. **Конфлікт ≠ завжди помилка:** система виявляє, пояснює, попереджає і за наявності права дозволяє свідомий override із записом причини в аудит.
3. **Правильний календар:** тижні рахуються від початку семестру, парність ODD/EVEN/BOTH, кожен семестр з тижня 1.
4. **Excel «як для друку»:** дворядкова сітка odd/even, об'єднання клітинок, друк Landscape.
5. **Швидкість:** Redis-кеш розкладів з інвалідацією при змінах.

## 5. Обсяг (scope)
**У скоупі MVP:** довідники → академічний календар → ядро розкладу → конфлікти + override + audit → Redis → Excel-експорт (розділ 111 ТЗ).
**Поза MVP (майбутні модулі, розділ 107):** Telegram-бот, push, автогенератор розкладу, SSO/LDAP, мобільний застосунок, LMS-інтеграція.

## 6. Обмеження й припущення
- Стек рекомендований, не обов'язковий: Python/FastAPI, PostgreSQL, Redis, React/TS, openpyxl, Docker.
- Права перевіряються на backend, фронтенд не є джерелом довіри.
- Система має працювати з «неідеальними» реальними даними (розділ 113), а не ламатися.

## 7. Критерій успіху (високий рівень)
Реальний друкований розклад університету можна завантажити, перевірити на конфлікти, відредагувати і вивантажити назад у Excel без втрати нестандартних випадків. Деталізація — у SMART-цілях (спринт 1).
